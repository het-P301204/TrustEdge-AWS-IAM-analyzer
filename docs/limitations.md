# TrustEdge limitations

Read this before treating an empty findings list as an all-clear. An empty
result means *nothing TrustEdge checks was found*, which is a much smaller
claim.

Every limitation below is also emitted in the report itself, on the finding it
applies to, so it travels with the thing someone is about to act on.

---

## 1. What TrustEdge is not

* **Not proof of exploitability.** It reports reachable trust paths from the
  trust policy's perspective. It never executes anything, never calls AWS, and
  never validates that a path works end to end.
* **Not an implementation of IAM authorisation.** Blast radius is an
  approximation. See §4.
* **Not a replacement for IAM Access Analyzer.** Access Analyzer applies
  automated reasoning to live resource policies across fifteen resource types
  with a defined zone of trust. TrustEdge grades condition strength on role
  trust policies, offline, and ranks it against blast radius. Run both.
* **Not an intra-account escalation graph.** Same-account assume paths are
  graded `INTERNAL` and excluded from the ranked findings by default.
* **Not a compliance tool.** No control mappings, no evidence workflow, no
  register.

## 2. What the input cannot tell it

| Cannot determine | Consequence |
|---|---|
| Who controls an external AWS account | A vendor relationship cannot be confirmed as current or appropriate. `vendor_accounts` is an operator assertion and is labelled as one in every finding that uses it. |
| Who operates an OIDC issuer or SAML IdP | An issuer not in AWS's shared-provider list is treated as private. If it is actually a multi-tenant SaaS AWS has not catalogued, the real exposure is **higher** than graded. The finding says so. |
| Whether an external ID was generated by the third party, or is unique per tenant | Both are AWS requirements. TrustEdge only checks guessability. A value can pass every check and still be shared across all of the vendor's customers. |
| Whether an IAM OIDC or SAML provider still exists | A trust policy referencing a deleted provider is unusable, not dangerous. TrustEdge notes when the referenced provider is absent from the export, and can say nothing if the export omits the provider lists entirely. |
| The identity provider's own role-assignment rules | For SAML and enterprise OIDC these are usually the real access control, and they live outside AWS. |
| Cluster RBAC, namespaces and which workloads use a service account | An IRSA subject condition can look correct and still be reachable from a namespace where untrusted workloads can create pods. |
| Trust anchors, issued certificates and imported CRLs | A pinned trust anchor is only as trustworthy as the CA behind it. Revocation for Roles Anywhere is imported-CRL only. |
| EKS pod identity associations, instance-profile attachments, function configuration | Which workloads actually hold a compute-attachment role. |
| Whether the caller's own account permits the call | AWS requires an Allow in **both** the identity policy and the resource policy for cross-account access. TrustEdge sees your side only. |
| Anything about accounts other than the one exported | Multi-account trust graphs are future work. |

## 3. Trust-policy features not evaluated

* **`NotPrincipal`.** The allowed set is the complement of the listed
  principals, which is not something to grade by guesswork. Statements using it
  are flagged for manual review, the confidence on the finding drops to `low`,
  and the grade shown may not reflect the real allowed set.
* **`NotAction`** in a trust policy. Treated as granting an assume-role action
  (the conservative reading) and flagged.
* **`Deny` statements in trust policies.** Counted and disclosed, not graded.
  TrustEdge does not compute how a trust-policy `Deny` narrows the `Allow`
  statements beside it.
* **Condition keys TrustEdge does not recognise.** Not credited as guards. If
  one of them does bound identity, the real exposure is *lower* than graded —
  the finding says this explicitly.
* **`CanonicalUser` principals.** A canonical user id cannot be mapped to an
  account offline, so the relationship is reported as `NOT_DETERMINED` rather
  than guessed.
* **Policy `Version` other than `2012-10-17`.** Graded with 2012-10-17
  semantics, with a warning.

## 4. Blast-radius approximation

**Implemented:** `Allow` statements from inline policies and from attached
managed policies whose documents are in the export; IAM glob action matching;
`NotAction` as "everything except"; resource breadth (`*` versus a named ARN).

**Approximated:** Only an *unconditional* `Deny` on `Resource: "*"` suppresses
a capability. Conditional and resource-scoped denies are counted and disclosed
but not applied — guessing whether a scoped deny covers the resource an
attacker would choose trades false positives for false negatives, which is the
worse trade for a security tool.

**Not evaluated at all:**

* Permissions boundaries. A role with one has narrower effective permissions
  than reported; the finding names the boundary ARN so you can check.
* Service control policies and resource control policies.
* Session policies passed at assume time.
* Conditions on `Allow` statements. A capability granted only under a condition
  is recorded with `conditioned: true` and still counted.
* Resource-based policies in other accounts, which can grant a role access its
  own policies do not show — this direction makes blast radius an
  **under**-estimate.
* Group membership (roles have none, but a converted export might carry it).
* `iam:PassRole` target resolution. TrustEdge records the resource patterns but
  does not resolve which roles are actually passable, or what those roles can
  do. So `passrole_plus_compute` says "the union of its own permissions and
  every passable role's" without computing that union.

**The bottom line:** `HIGH` or `ADMIN` means the role's own policies grant
those capabilities, not that an attacker has been proven able to use them.
`UNKNOWN` means no policy document was resolvable, which is deliberately not
`LOW`.

## 5. Grading limitations

* **The weights and severity bands are a defensible ordering, not a published
  risk model.** They are documented in
  [methodology.md](methodology.md) precisely so you can disagree with them
  concretely.
* **Providers without a bespoke subject grammar** are graded by counting fully
  pinned `:`/`/`-delimited segments. That is a structural heuristic, disclosed
  on every finding that uses it. GitLab in particular has no bespoke parser in
  this version because its subject grammar was not verified from primary
  documentation — see [research.md §7](research.md#7-what-is-verified-what-is-inferred-what-was-removed).
* **The GitHub claim→condition-key mapping can change.** TrustEdge flags keys
  outside AWS's documented mapping as `undocumented_condition_key` with an
  explicit "cannot confirm" caveat, rather than asserting they are invalid.
* **The compute-attachment service list is curated, not exhaustive.** A service
  principal that behaves like a compute attachment but is not on the list will
  be graded `MODERATE` as a confused-deputy review item. The list is a named
  table in `providers/aws.py`; add to it and tell us.
* **A `NotAction`-only Allow on `Resource: "*"`** is treated as
  administrator-equivalent when the exclusion list still leaves
  `iam:PutRolePolicy` reachable. That is a heuristic reading of an uncommon
  construct.

## 6. Known false-positive sources

Named so you can argue with them rather than discovering them:

1. **Service principals with no source condition.** Not every AWS service
   populates `aws:SourceAccount`/`aws:SourceArn`, and some integrations have
   their own confused-deputy protections. AWS says to check the service's own
   documentation. Reported as `MODERATE`, never as `OPEN`.
2. **Private-issuer classification.** An issuer TrustEdge treats as private
   might be shared. This direction produces a false *negative*, which is worse
   — hence the explicit limitation on every private-issuer finding.
3. **`undocumented_condition_key`.** A condition on a key AWS does not populate
   fails closed under a normal operator. The policy is not doing what its
   author intended, but it is not permissive either.
4. **Unrecognised condition keys on a wildcard principal.** Graded `OPEN`
   because they are not credited. If one bounds identity, the grade is too high.
5. **Vendor / trusted-account assertions.** Populating them lowers grades. A
   wrong assertion causes a false negative.

## 7. Known false-negative sources

1. **Unresolved managed policies.** Blast radius is a lower bound, reported as
   `UNKNOWN` or with a "lower bound" note.
2. **Boundaries not evaluated in either direction.** A role could be broader
   than reported via a resource policy elsewhere.
3. **`NotPrincipal` statements.** Not graded.
4. **Conditions TrustEdge credits as guards but which do not hold in practice**
   — for example a principal tag set by an untrusted account's administrators.
   TrustEdge grades `aws:PrincipalTag` on a wildcard principal as `WEAK` for
   exactly this reason, but a tag condition on a cross-account principal is
   credited more generously.
5. **Trust decay.** TrustEdge cannot tell you that a relationship is stale.
   `create_date` is carried through the export but is not used in grading.

## 8. Operational limitations

* An IAM authorisation export is sensitive: it is a complete map of who can do
  what. Treat it accordingly. TrustEdge never transmits it; `trustedge serve`
  parses it in memory, binds loopback by default, and writes nothing to disk.
  Binding `serve` to a non-loopback address exposes an unauthenticated viewer
  and the tool warns when you do.
* Analysis is single-threaded and in-memory. A very large account produces a
  large report; use `--max-findings` for the Markdown and the JSON for
  everything.
* `trustedge convert` picks a managed policy's **default** version. If the
  export's `PolicyVersionList` is incomplete or the default is unmarked,
  TrustEdge warns and falls back to the first version — which may not be the one
  in force.
